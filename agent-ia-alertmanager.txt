QUESTIONS / RÉPONSES
------------------------------------------------------------------------

Q1. Comment l'agent recevra-t-il les alertes ?
R1. AlertManager sait envoyer les alertes vers un "webhook receiver".
    L'agent sera un petit service HTTP dans le cluster qui reçoit ce
    POST, puis enquête (kubectl, logs) et produit un diagnostic.
    Question ouverte posée : de quoi le pod aura-t-il besoin pour
    enquêter, et quel risque de sécurité ça pose ? (indice : identité
    du pod → ServiceAccount / RBAC)

Q2. Je n'ai jamais utilisé AlertManager, c'est quoi ?
R2. Il tourne déjà dans le cluster (installé par kube-prometheus-stack,
    namespace monitoring).
    - Prometheus évalue des règles d'alerte (ex. "pod en
      CrashLoopBackOff depuis 5 min") et envoie les alertes déclenchées
      à AlertManager.
    - AlertManager les regroupe, déduplique et les ROUTE vers des
      receivers : email, Slack... ou un webhook (c'est là qu'on
      branchera l'agent).

Q3. AlertManager est un pod ?
R3. AlertManager est une APPLICATION (binaire Go, comme Prometheus) qui
    tourne dans un pod : alertmanager-kube-prometheus-stack-alertmanager-0.
    - Le "-0" indique un StatefulSet (créé par le Prometheus Operator),
      pas un Deployment.
    - Le "2/2" = 2 conteneurs : AlertManager + un sidecar
      config-reloader qui recharge sa config à chaud.
    Question ouverte posée : pourquoi un StatefulSet plutôt qu'un
    Deployment pour ce genre de composant ?

Q4. Contexte d'accès : Claude Code tourne sur un serveur Ubuntu, David
    y est connecté en SSH.
R4. Conséquence : un `kubectl port-forward` ouvre le port sur le
    SERVEUR, pas sur la machine de David → son navigateur ne voit rien
    sur localhost:9093.
    Bonne approche : le pattern Grafana/Prometheus — un Ingress Traefik
    + une entrée `alertmanager.remote` dans le /etc/hosts de la machine
    cliente.
    Exercice donné : écrire un manifeste Ingress pour AlertManager en
    s'inspirant de l'existant (kubectl get ingress -n monitoring -o yaml).
    Infos : namespace monitoring, service kube-prometheus-stack-alertmanager,
    port 9093. À montrer avant d'appliquer.

Q5. Quel lien entre Grafana/Prometheus et AlertManager ?
R5. La chaîne complète :

    node-exporter, kube-state-metrics... → Prometheus → AlertManager → toi
        (exposent les métriques)   (collecte + évalue  (route, groupe,  (email, Slack,
                                    les règles)          notifie)         webhook...)
                    Grafana --lit--> Prometheus

    - Prometheus est le cerveau : collecte les métriques, évalue les
      règles, DÉCLENCHE les alertes.
    - AlertManager ne détecte rien : il gère la LIVRAISON (regroupement,
      silences, routage vers les receivers).
    - Grafana est à part : pure visualisation, il lit Prometheus, il
      n'est pas dans le chemin des alertes.
    Question ouverte posée : pourquoi séparer Prometheus et
    AlertManager ? (indice : 3 serveurs Prometheus qui détectent la
    même panne → déduplication)

NOTIONS VUES (2026-09-09 aprem) :
- Le "menu" : Mistral ne voit JAMAIS le code Python des tools. Son seul
  lien avec eux = la description JSON qu'on lui passe. À partir de ça il
  décide QUOI appeler et avec QUELS arguments.
- `properties` est indispensable : c'est ce qui permet à Mistral de
  fabriquer le JSON d'arguments (noms EXACTS des params, types, sens).
  Sans lui → Mistral croit que la fct ne prend rien → appel à vide →
  TypeError missing argument. `required` dit lesquels sont obligatoires.
- Le défaut de `namespace` est géré par la SIGNATURE Python
  (def get_pod_events(pod_name, namespace="default")), pas par le schema.
  Le schema ne fait que documenter (namespace hors de `required`).
- "default" dans la description = le NOM du namespace k8s, pas un mot-clé.
- Chaîne longue en Python : pas de continuation avec `/` ni `\` dans le
  texte. Soit une seule ligne, soit concaténation implicite de chaînes
  adjacentes entre parenthèses :
      "description": (
          "phrase 1 "
          "phrase 2"
      ),
- La variable EST le dict : `TOOL_X = { "type": ..., "function": ... }`
  — une seule paire d'accolades, pas un dict qui enveloppe un dict.
- Choix d'Ollama vs alternatives locales (llama.cpp brut, vLLM pour
  servir à plusieurs/GPU, LM Studio, LocalAI) : Ollama gagne ici car
  pull + API REST :11434 + paramètre `tools` natif, zéro config. On
  regarderait vLLM si l'agent devait encaisser beaucoup d'alertes en //.

MÉCANIQUE DE LA BOUCLE AGENT (à coder ensuite) :
  1. messages = [ {role:"user", content: <l'alerte / la demande>} ]
  2. appel Ollama chat avec messages + tools=[les 3 dicts]
  3. la réponse contient SOIT du texte (=> fini, on affiche) SOIT des
     message.tool_calls (nom + arguments JSON)
  4. si tool_calls : pour chacun, exécuter la fct Python correspondante,
     append {role:"tool", content: <résultat>} dans messages, puis
     RE-boucler en 2
  5. sinon : sortir, afficher message.content
  Le LLM ne fait rien lui-même : il DEMANDE, c'est notre code qui exécute.
